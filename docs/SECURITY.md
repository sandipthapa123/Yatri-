# Security

What the system defends against, where each defence lives, and how it is checked. This is the audit's
result for Phase 12; the operating rules are in `docs/OPERATIONS.md`, and the authentication design in
`docs/AUTHENTICATION.md`.

Principles (they are also in `CLAUDE.md`): the backend is authoritative, so a client is never trusted to decide
who someone is, what they may do, what a fare is, or where a ride stands; location is sensitive and is kept
only as long as a ride needs it; nothing secret or personal is written to a log or an error message.

## Issues found and fixed in this audit

| Finding                                                                                                                                         | Fix                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Access-token algorithm and issuer were not pinned (the library default was accepted)                                                            | Pinned in the API and the admin console, from one shared definition                                                                              |
| Rate-limit counters were incremented and expired in two steps: a crash between them left a counter that never expired (a permanent block)       | One atomic script; it also repairs an existing counter with no expiry                                                                            |
| No ceiling on the API as a whole; several state-changing routes (chat, saved places, vehicles, documents, admin, profile edits) had no limit    | A per-address ceiling and a per-user mutation limit on every authenticated router                                                                |
| Profile-picture uploads and account deactivation had no rate limit                                                                              | 10 an hour and 5 an hour                                                                                                                         |
| Driver location and online/offline endpoints were limited **per address**: drivers on a shared mobile-carrier address would throttle each other | Limited per signed-in user                                                                                                                       |
| Unhandled errors were printed raw (a database or provider error can carry row values or a URL with an API key)                                  | One redacting logger; errors written as name, message, code; correlation id returned to the caller                                               |
| A malformed JSON body produced a 500                                                                                                            | 400 `INVALID_JSON` (and 413 for an oversized body)                                                                                               |
| Staging was configured like development: the OTP bypass and console SMS were only refused in production                                         | Staging obeys production's rules; CORS and public URLs must be https and non-local; secrets must differ; a seeded admin is refused in production |
| A slow or stuck query or a hung Redis command could hold a request indefinitely                                                                 | Database statement timeout and pool bounds; Redis command timeout with capped backoff                                                            |
| Only a liveness probe existed (a database outage was invisible to the load balancer)                                                            | Readiness check of database and Redis with a deadline; liveness kept separate                                                                    |
| No graceful shutdown: a deploy dropped connections and left the pool open; an escaped rejection had no record                                   | Orderly stop with a deadline; escaped errors are logged then the instance restarts                                                               |
| Duplicate and redundant database indexes slowed every write (including the driver's location, written every few seconds)                        | Removed; a test now fails if a duplicate index reappears                                                                                         |

## Residual risks (known, accepted or open)

- **No push provider and no hosted error tracker.** Notifications reach a person only when the app is open (they
  are stored and readable); a closed app is not woken, which matters most for ride offers and SOS follow-up.
  Choose and connect both before a public launch.
- **Admin lock-out by guessing.** Ten wrong passwords for one admin email in 15 minutes blocks that address's
  logins for the rest of the window (an attacker can therefore cause a nuisance lock-out); the trade is
  deliberate and the window is short. Per-address limits also apply.
- **Refresh tokens rotate but reuse is not treated as theft.** A stolen refresh token used after its owner
  refreshed simply fails; it does not revoke the family. Suspending the account ends every session.
- **The admin console has no script CSP.** Next.js needs inline scripts and a policy that has not been exercised
  in a real browser would break sign-in; frame, referrer, sniffing and transport headers are set. Add a
  nonce-based CSP together with a browser test.
- **Search on names is a scan** (case-insensitive substring). It is fast at current size; at large scale add a
  trigram index (needs the `pg_trgm` extension).
- **Emergency contacts are not consent-verified**; a wrongly typed number would receive a link after an SOS.
- **Not tested:** behaviour under real network partitions and on real devices, a penetration test by a third
  party, and load beyond the seeded test dataset. Do an external penetration test before launch.
